# Database design

All primary keys are UUIDs generated by the application and represented with SQLAlchemy's backend-compatible UUID type. `created_at` and `updated_at` are UTC timestamps on mutable domain entities; audit logs are append-only and have only `created_at`. Mutable records use `is_active` and, where user-facing deletion is expected, `deleted_at`.

## Tenant and branch isolation

`companies` is the tenant root. `branches`, `financial_years`, and company-scoped roles belong to a company. `user_companies` grants a user access to companies, while `user_branches` grants branch access. `user_branches` uses a composite foreign key `(branch_id, company_id)` to `(branches.id, branches.company_id)`, making it impossible to assign a branch under the wrong company even when IDs are supplied manually.

## Relationships

- Company 1:N Branch
- Company 1:N FinancialYear
- Company 1:N Role (nullable company permits system roles)
- Role M:N Permission through RolePermission
- User M:N Role through UserRole
- UserPermissionOverride provides scoped grant/deny exceptions; branch scope
  always includes its company scope.
- User M:N Company through UserCompany
- User M:N Branch through UserBranch
- Company/User/Branch 1:N AuditLog (actor and tenant use `SET NULL`; branch ownership is enforced by the composite key)

## Permission evaluation

Permissions use `module.resource.action` codes. Active user overrides are
evaluated before active role grants, with the most-specific scope winning and
denies winning ties. System roles (`company_id IS NULL`) are global; other
roles only apply inside their company. Every company/branch request also
requires the user's corresponding `user_companies`/`user_branches` grant.

Financial years enforce `start_date < end_date` and unique company/name and company/start-date pairs. Detecting overlapping periods requires a service-level validation on SQLite and a PostgreSQL exclusion constraint can be introduced when the accounting module defines its date-range semantics.
